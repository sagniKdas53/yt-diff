## Phase 0b results (laptop)

The review defines this test on a phone. This is the same pair on a laptop with
an Intel i5-7200U, HD 620 and GeForce 940MX. Both videos are from the archive,
and bitrates come from file size and duration.

| File                | CPU temperature | What the owner saw                  |
| :------------------ | :-------------- | :---------------------------------- |
| AV1 2160p, 9 Mbps   | Up to 65°C      | Lags. Seeking and jumping lag too   |
| H.264 1080p, 7 Mbps | About 53°C      | No lag reported. Smoother on origin |

**Reading:** the AV1 file points to the client, not the server. Neither GPU has
AV1 hardware decoding, so any browser has to decode it on two CPU cores.

**The player doesn't choose a decoder.** It's a plain `<video>` element with a
direct file URL, so the browser decides. The original site isn't a fair
comparison, because it picks a stream to suit the device and the file here is
served as is.

**Not checked:** whether the browser used the GPU for H.264. Linux browsers
often leave this off. The `chrome://media-internals` page names the decoder in
use.

**What it means for the plans:** nothing changes yet. Plan 03 Task 5 already
warns about a file that may stutter. If phones lag on AV1 as well, "quality
first" and the decision against transcoding are worth another look, and that's
the owner's call.

## Found along the way, not fixed

- 230 `raw_metadata` rows store a `cookies` value, and so do the backups. They
  hold site session cookies. 28,062 rows store `http_headers`, none with a
  `Cookie` header.
- `user_accounts` has 228 duplicate unique constraints on `username`. Booting
  the app twice against the test database added one, so it's one per boot, from
  `sync({ alter: true })`.
- `approximateSize` can't be trusted: it totals 8.7 GB for a 361.5 GB library,
  and some values are negative.

## Where the storage is (measured 2026-11-06)

361.5 GB in 8,068 files: 343.9 GB of MP4, 17.3 GB of WebM, 0.2 GB of MKV.

| Could be reclaimed                                    | Size    |
| :---------------------------------------------------- | :------ |
| Orphan files no row points to (198, 42 of them video) | 3.93 GB |
| Identical sizes, files over 10 MB (1 pair)            | 0.19 GB |
| Same site and video id downloaded twice (13 groups)   | Unknown |
| Same URL with different spelling, both saved (9)      | Unknown |

The last two overlap, and they're at most a few dozen files, against 2,658 video
files. Filing frees nothing, because each URL already has one file. No database
reference is missing from disk. Rerun `seed/audit.sql` for the query side.

**The dedup tool already exists.** `/dedup-unlisted` and `/dedup-playlists`
merge duplicate rows, moving mappings to the row they keep. They don't delete
the duplicate's file, so they free nothing, and a merge can leave an orphan
behind. That may explain some of the orphans above. 121 same-id groups remain.

Duration across Unlisted is known for 1,376 of 3,430 rows.

## Running in cloud sessions (parked)

From the documentation on 2026-11-06. None of it has been tried in a real
session.

- Deno isn't preinstalled. `deno.land` and `cdn.skypack.dev`, both in
  `deno.lock`, aren't on the Trusted allowlist, so the environment needs Custom
  network access.
- PostgreSQL 16, Redis, Docker and Chrome are preinstalled. Services aren't
  running until started, and that has to happen every session.
- `gh pr` and `gh issue` fail because the proxy blocks GraphQL. `gh api` works.
- `.claude` and `.gitnexus` aren't in the repository, so GitNexus, skills and
  plugins aren't there. Repository-declared plugins don't load in cloud
  sessions.
- API access covers attached repositories only, so frontend work needs
  `yt-diff-react` attached. Submodule init and push are untested.
- The Pi and the Forgejo remote are unreachable, so backfills stay manual.
